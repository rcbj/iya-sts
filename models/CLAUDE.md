# models/

The common model (#1390, closed 2026-11-10; the real OID root was #1573; the gaps #1390 left, and every protocol family, were #1579). **The whole directory namespace is switched.** Every object is
written by hand in `directory/*.tsp`, the directory's three name lists
(`STANDARD_NAMES`, `OWN_NAMES`, `SECRET_ATTRIBUTES`) are `directory/names.tsp`, and
the owning module reads what the build generates, through
`common/model_tables.ts`. **Persistence is switched too**: every PostgreSQL and
MariaDB table and index is in `persistence/*.tsp`.

**How a switch was made, for the next object.** A one-time conversion wrote the
table as TypeSpec with its comments, `generate.mjs` produced the file, and the
file was compared with the JSON of the original literal: byte-identical, 171,311
bytes for `Application`. Only then was the literal removed. The object goes in
`ModelEmit`'s `AUTHORED` and `models/main.tsp`, and its id in
`compiled_tree.js`'s `GENERATED`, which refuses a tree without the file
(`STS-CORE-0093`). The module then asks `ModelTables.schema(id)`. `@entry`'s `authored: true` says `kind` is the author's.

**Where the code still holds part of a table, on purpose.**

* **A policy's `FIELDS` is the model's `field` values** (`ModelTables.fields()`),
  which is where type, default, min, max, label and allowed values live now. A
  value the code computes, such as a limit `common/crypto.js` owns, is not in the
  TypeSpec: the module passes it in by row key.

**A register the code branches on is the model's too (#1579).** `@entry` takes
`terms` (a closed list whose values carry a label and a sentence; its ids are a
list as well, so `allowedFrom` may name it), `pairings` (for each value of some
lists, the values of others it permits), `mechanisms` and `doors`. They are
generated into `directory.facts.json`, which `ModelTables.facts()` reads:
federation's `MECHANISMS`, `SUBJECT_POLICIES` and `MANAGEMENT_FOR_KEY`, the
authentication policy's `MECHANISMS` and the service-account policy's `DOORS`
are the model's rows, and the code keeps only what each id DOES. The policies'
per-mechanism and per-door settings are still built by the module from those
rows (the `computed` argument of `ModelTables.fields()`), each taking its
sentence from its attribute: that is a projection of model data, not a second
writing. `generate.mjs` refuses a pairing whose value is in none of the lists
it names, a key it says nothing of, and an id stated twice (`checkFacts()`).
`tests/model_registers.js` holds each register to its behaviour: every id has a
reader in the service source, and every literal at the named call sites is an
id.

**What a console may change is each row's `editable`** (`set`, `multi`), under
`@entry`'s `editing: true`, which gives every row of the table an `editable`,
last, false where the row says nothing. `application.tsp` and
`federation_relationship.tsp` carry it, with the reasoning that headed the
`EDITABLE` tables the two modules used to merge onto their rows after loading.

**`postgres/schema.sql` and `mariadb/schema.sql` are generated files that are
committed**, because `docker-compose.yml` mounts one from the host. A change to a
table or a template owes `tests/tools/regenerate-model-docs.sh`, and
`tests/model_typespec.js` fails until the committed script matches. A column added
after a table first shipped is marked `@column(#{added: true})`, and the driver's
`SCHEMA_COLUMNS` is read from `persistence.postgres.json`'s `added`. The other
migrations stay in the driver (`SCHEMA_UPGRADES`, the routines): they are history,
not shape, and the test holds each upgrade to the column the model says the table has.

**Things that can catch you.** A module may not add to a table it loads:
`tests/model_typespec.js` holds every authored object's loaded table to its
generated file. `--strip` removes `models/lib`, `models/tools` and every `.tsp` from the shipped
image, which keeps `models/generated/`.

**The equivalence, and the test that holds it.** The importers read the
code, `common/model_emit.ts` writes the TypeSpec, and `tests/model_typespec.js`
compiles it with `@typespec/compiler` and rebuilds the sources from the compiled
program: every `SCHEMA` table, equal to the one in code, and every statement of
`postgres/schema.sql`, in order. It also edits a copy of the TypeSpec and
requires the edit to reach the SCHEMA, the class and the DDL. That is the
equivalence #1390 required before anything was switched, and still holds.

**The compiler is a dependency of `tests/` only.** It is pinned in
`tests/package.json`, so it is in the tests image and in the `typescript` build
stage, and never in the shipped image.

**A value a decorator takes is closed.** `model_lib.tsp` declares every key; an
undeclared one is a compile error. A new fact about an attribute is added there.

**What each importer does, and what it does not.**

* `common/directory_model.ts` reads each object's generated table. Spellings
  and the secret list are read as text from `directory/names.tsp`, for the
  comments above each name.
  `kind` is what the module declared, or what the attribute's RFC says when the
  module says nothing; `declaredKind` keeps the difference. `withheld` is true
  for `sensitive`, for `secret`, and for anything in `SECRET_ATTRIBUTES`.
* An OID, syntax or matching rule for a published name comes only from
  `rfc_schema.json`. **This service's own names are numbered in
  `directory/oid_register.json`**: `<root>.1.1.n` for an attribute, `<root>.1.2.n`
  for a class. A number is assigned once and never reused, and a new name takes the
  next one (`tests/model_directory.js` fails on a name with neither).
  **`root` is `1.3.6.1.4.1.67607`, Iya CyberSecurity Solutions' IANA Private
  Enterprise Number** (#1471, assigned 2026-11; the swap was #1573), and
  `placeholder` is `false`. Until then it was `1.3.6.1.4.1.32473`, the number
  RFC 5612 reserves for documentation; the numbers under the root did not change.
  **Nothing published may carry RFC 5612's number while `placeholder` is false**:
  `tests/model_directory.js` fails on one in the catalogue, the RFC 4512
  definitions or any page under `docs/`, and the *Directory models* page says the
  OIDs are placeholders only while the register does. A name somebody else
  publishes is in the register's `publishedElsewhere` and stays without one.
  RFC 4512 requires a syntax, and nothing states one for our names, so they take Directory String, and a
  class is auxiliary beside a published structural class and structural otherwise.
* `common/postgres_import.ts` keeps each column's type and its clauses, and each
  statement's place in the script. Indexes hang off their table; everything else
  the script runs is on `PostgresSchema`, as text.
* `common/mariadb_import.ts` and `common/openapi_import.ts` still only capture
  their sources. `emit()` there returns the bytes it was given, so a test that
  compares it to those bytes proves nothing.

**`domain/*.tsp` are the canonical domain models (`lib/domain_lib.*`).** A directory object says how something is STORED; a concept says what it MEANS, and each field states where it comes from (`@fromAttr`), how it is worked out (`@derived`) or that it is a concept read from the same entry (`@embedded`). The protocols stay separate concepts on purpose. `generate.mjs` refuses to build when a field names an attribute nothing declares, reads a sensitive attribute without saying `secret: true`, or takes one value of a multi-valued attribute without saying `transform: "first"`. `common/domain_map.ts` turns an entry into a concept from `models/generated/domain.json` and leaves a secret out unless the caller names it; `fieldOf()` reads one field the same way. **A User carries no credential**: a credential will be a concept of its own, so passing a User around cannot carry one. `tests/model_domain.js` holds the refusals and the mapping. **A concept may be held on a record instead of an entry** (`record:` and `@fromRecord`), for what is not in the directory at all: Session, AuthenticationEvent, IssuedToken and AuditEvent. No directory object stands behind those at build time, so `tests/model_domain.js` holds each to a real record made by the code that owns it. The catalogue covers the Identity, Application, Authorization, Federation, PKI, Session, Authentication, Token, Audit, Policy and Directory areas, and **the build refuses an attribute no concept reads**. `common/domain_classes.ts` and `types/api.generated.d.ts` are generated and committed (`tests/tools/regenerate-model-docs.sh`); `@projects("Concept")` ties a published API shape to the concept it is a view of. A concept's boolean is true for `true` in any case and an integer must be all digits, so a stored value that is neither is absent rather than guessed. No directory-object member is typed `unknown`. **The service reads them through the concept** (#1579): a session through `authn.sessionView()` (the session lists, the sign-out inventory, the recent-sign-in checks, the authorization response, SAML's and WS-Federation's AuthnInstant), a token register row through `IssuedToken.fromRecord()` (the sign-out inventory, OpenID Provider Commands), an audit row through `AuditEvent.fromRecord()` (the audit export's event, the audit view's filter). The writers build the records with the concept's keys, and the stored rows and the export's wire format did not change, with one exception: a token row's `client_id` is always a string, the first audience when a token names no client and several audiences (rcbj, #1579, 2026-11-11; it was the array, which `IssuedToken.clientId` could not read); `tests/model_domain.js` fails when one of those readers stops asking the concept, and holds the export's event byte for byte. A record member nobody can list ahead (an audit row's `detail`) is `Record<unknown>`, which only a record may hold. Two things are read off the record on purpose: what rides on a session (each family's own: `oidcClients`, `wsfedRealms`, the SAML service providers, the device binding) and whether a relying-party session holds a refresh token, because the concept never carries a token. `DomainMap.fromRecord()` works each concept's plan out once, so a session costs about 2 microseconds. The catalogue covers the Identity, Application, Authorization, Federation, PKI, Session, Authentication, Token, Audit, Policy and Directory areas, and **the build refuses an attribute no concept reads**. `common/domain_classes.ts` and `types/api.generated.d.ts` are generated and committed (`tests/tools/regenerate-model-docs.sh`); `@projects("Concept")` ties a published API shape to the concept it is a view of. A concept's boolean is true for `true` in any case and an integer must be all digits, so a stored value that is neither is absent rather than guessed. No directory-object member is typed `unknown`.

**Request validators are generated (`common/model_zod.ts`).** An Account API or Authentication API operation's body and query are `ModelZod.body()` and `ModelZod.query()` of its own operation in the model, so the refusal and the document are one declaration. It refuses a JSON Schema keyword it does not understand. An integer is coerced, because a query or form holds a string; `format: "uri"` binds `validation.types.uri`, the one check JSON Schema cannot state. Since #1579 it also reads `oneOf`, `patternProperties`, `uniqueItems`, `maxProperties`, OpenAPI 3.0's `nullable` and a component `$ref` (recursive ones lazily), and `ModelZod.component(doc, name, { typed: true })` is one component's validator with no coercion, for a JSON document.

**Two lists in the Account API are the code's, written into the document at build time (#1579)**: `changeCertificates`' `profile` values (`$enumFrom` `common/enrollment_profiles.js`'s `CHALLENGE_PROFILE_IDS`) and `changeAppPasswords`' `door_<id>` members (`$membersFrom` `common/app_password_doors.js`'s `DOOR_IDS`). Both are data the service decides with in more places than this API — four enrollment protocols and a realm's name, five password doors — so the source is the requires-nothing data leaf, which `lib/api_lib.mjs` can read before any TypeScript is compiled, and the document, the validator and the API types follow from it. A profile or a door is added in that file only.

**No hand-written validator stands in front of a modelled operation (#1579).** The enrollment consoles' actions (`acme_console.ts`, `est_console.ts`, `scep_console.ts`) are `ModelZod.body()` of their Management API operations, SCEP's views and `/admin/oauth2/monitor`'s query are `ModelZod.query()` of theirs, and the revocation-reason lists those consoles show are read from their operations: the model grew the identifier, serial, profile and challenge-id patterns, the minimum lengths and the page bounds the hand schemas checked, and **OpenAPI's `allowEmptyValue`**, which `ModelZod.query()` reads as `validation.types.opt()` did — an empty value is none. The `PAGE_QUERY` and `ACTION_FORM` schemas of `acme_admin.ts`, `est_admin.ts`, `gnap_admin.ts` and `scep_admin.ts` checked the server-drawn pages #446 removed, and are deleted with their codes retired. The portal's CIBA answer is `answerSignInRequest`'s body, still checked inside its handler because `LimitsForm.strip()` has to take the GNAP limit controls off first (the model names them as `patternProperties`). **The Reports API's query document** is `QueryDocument` and the six `Filter*` forms: `report/query.ts` reads the model's issues for where a document is wrong and keeps each refusal's code, token and sentence, and keeps in code only what one document cannot answer — the catalog's sources, fields, flags and operators, a value's type for its field, a saved parameter, a field ordered twice (two distinct entries to JSON Schema), a count's grouping, how deep a filter nests (JSON Schema bounds no recursion) and the size caps. A definition, a share and a run's parameters are held to `DefinitionWrite`, `ShareWrite` and `ParameterBag` at `report_api.ts`'s door; **a parameter name's length (1 to 64) stays in `report/jobs.ts`, because the Reports API OpenAPI document is 3.0.3 and has no `propertyNames`.**

**The API types type the handlers (#1579).** `types/api.generated.d.ts` holds, for each of the five documents, `IyaApi.<Api>.Operations`: every operation by its operationId (by `METHOD path` in the Reports API, whose operations carry none), with its JSON body (`{}` where it takes none, `unknown` for an upload), its query and its JSON answer at each 2xx status. `types/api-handlers.d.ts` binds a handler to its entry (its request and response are express's, and `tsconfig.json` maps `express` to its declarations so that is the same on every host and in the image), so `tsc` (`tests/typecheck.js`) refuses a handler that reads a body member or a query name its operation does not declare, or answers a member, a value or a 2xx status its answer does not allow. The query's NAMES are the model's and its values what express parsed, except where the route validated it first (the Account API's `input`, the model's types). The binding goes through the place each API keeps its handlers: the Management and Admin Console APIs' route table (`IyaApi.AdminRow`, a row typed by the operationId it names, a row of actions by `common/api_rows.ts`'s `ApiRows.actions()`, the console twins by both operations) and every table it spreads; `AccountOperation` (`types/account-api.d.ts`), and the page modules' helpers a handler hands its response to; the Authentication API's operation tables, read as constants, typing each handler method by the operations whose rows name it; and the Reports API's serving functions, each annotated with its operation. Past the handlers: **the admin-core views** an operation answers with return its 200 answer (`IyaApi.AdminAnswer`), or carry it as `json` beside the page's own members (`IyaApi.AdminView`); **the admin-core actions** a row of actions calls take the merged bodies of the model's POST operations one segment under their path (`IyaApi.AdminActionBody<'/admin-api/users'>`, found by the `method` and `path` each generated operation carries), and what an action reads that no operation declares is named where it is read (`IyaApi.NotInModel<…>`: older spellings like `user` beside `username`, and `actor`/`form` an in-process caller adds; the API's closed bodies let none of them through, so only a direct call such as a test sends them — each is a candidate for deletion); **the sign-in acts** `/authn-api` hands its response to (`authn/authn.ts`'s `screenAct()` and steps, `authn/email_factor.ts`, `oauth-oidc/consent_screen.ts`, `oid4vc/vc_signin.ts`) take `IyaApi.AuthnAnswering<…>` of their operations, and the answer helpers they share (`stepAnswer()`, the refusals) any of the API's. Each sender (`sendJson()`, `ctx.json()`, `answerJson()`, `reportJson()`) checks the answer where the status is a literal. **Left to the runtime check (`common/response_models.ts`), because one value cannot name its status:** every `result.ok ? 200 : 400` answer (most `POST …/:action` rows), `/authn-api`'s sign-out acts (`logout/logout.ts`'s `signOutAct()` and `signOutAccountsAct()` hand back `{ status, json }`), and the refusals that take their status from the failure. **Not typed:** `admin-core/admin_views.ts`'s `directoryPageJson()`, whose `name` argument picks which of seven answers it builds (each handler hands the answer to a function typed by its own model shape); `IyaApi.NotInModel` members, which the model says nothing of. The generator types an open object (`additionalProperties`) with an index signature, and a constraint-only `anyOf` as the object it constrains. `tests/model_api_handlers.js` edits a real handler, view, action and act of each API in a scratch copy and requires `tsc` to refuse it, and holds every one of them to a typed place.

**What every operation of a document takes is stated once, as `x-iya-every-operation` in its `@apiDocument`** (#1476, #1483), and `lib/api_lib.mjs` adds it to each operation after the operation's own parameters: `DPoP` and `cell` on the Management API and Admin Console API OpenAPI documents, `DPoP` and `X-Requested-With` on the Account API and Reports API OpenAPI documents, `X-Requested-With` on the Authentication API OpenAPI document. **Examples live on the operation in the model** (#1475, #1483): a routing row has no use for one, and an operation that deliberately has none says why in a comment above its `@endpoint`, because an example is executed.

**SCIM is the first protocol surface in the model (#1579).** A schema is a `@scimSchema` model, and the property's TypeSpec type carries what it can (type, multi-valued, required, sub-attributes, canonical values) so `@scimAttribute` carries only the rest of RFC 7643 section 2.2. A mapping row is `@maps` on the attribute it maps, numbered within its table because the row order decides where an untyped value goes. What the code still owns is argued in `scim/CLAUDE.md`: the conversions (a `kind` is a branch, not a shape), the one `transform`'s functions, and scimmy's spelling of two characteristics. **OAuth 2.0 and OpenID Connect are the second (#1579)**, in rcbj's order (SCIM, OAuth 2.0/OIDC, GNAP, AuthZEN, SSF, ACME/EST/SCEP, SPIFFE, SAML, WS-Trust/WS-Federation): a request is a model of parameters, an answer or a claim set a model of members, so a refusal and the shape it refuses are one declaration. What needs the client's registration or the realm's mode stays in code and reads the generated shape (`oauth-oidc/CLAUDE.md`). The holding of an answer records and does not refuse, because a specification's endpoint must not change; that is argued there and is rcbj's to reverse. **GNAP is the third (#1579).** Its requests are JSON documents rather than parameters, so a document is a model whose rendering is the JSON Schema `gnap/gnap_schemas.ts` compiles — the six rendered schemas were byte-identical to the hand-written ones before those were deleted — and the shared types are rendered once as every document's `$defs`. The registries the request walk branches on are `@registry` unions (and RFC 9493's formats a model of tuples), and the access-type catalogue's definition, shared with RFC 9396, is a member set `common/applications.js` reads its member list and `interaction` values from. Answers and error codes are held as OAuth's are, recorded under STS-GNAP-0910 and 0911. What stays in code is argued in `gnap/CLAUDE.md`. **AuthZEN is the fourth (#1579)**: a request is a model of fields, each checked in its declared order and refused with the code and sentence the model gives it, so the readers in `authzen/` hold no shape and no sentence of their own; the sentences are model data because every one of them is on the wire, and the switch kept them word for word. Fields a request reads between checks that need state are `deferred` and read by path at that place, which keeps the order without the code restating the shape (`authzen/CLAUDE.md`).

**The Shared Signals family is in the model (#1579).** An event type is a model whose properties are its payload members, and the TypeSpec type IS the shape `ssf_events.js`'s `checkMember()` holds a value to (`numeric`, `boolean`, `string[]`, `Record<string>` for CAEP's language maps, `Record<unknown>`, a union of literals for a closed list, the same with `string` for an open one), so a row's members, their order and their prose are one declaration; CAEP's four common members are a model spread onto each CAEP row. A subject format's members are closed and each names its check. What the code keeps is what a row does — each check's sentence, each event's payload generator — and what needs state; `ssf/CLAUDE.md` says which. Its documents are held as OAuth's are: recorded, never reshaped.

**ACME, EST and SCEP are in the model (#1579).** A request document is a `@body` model of members whose TypeSpec type carries what it can (required, array, boolean, integer, literal, a nested `@shape`) and `@field` the bounds in the order the check makes them, because a refusal's sentence quotes zod's first issue; a member's values may come from a register (`valuesFrom`), so the register stays the one source. A register is a `@register` model whose properties are its rows, in order: the code keeps only what each row DOES. EST's and SCEP's bodies are DER, so what is modelled of them is the facts the code reads — the operations, media types, statuses, capabilities and signed-attribute values — and the DER work stays in `est_codec.ts` and `scep_cms.ts`. ACME's answers and EST's nonce answer are held as OAuth's are: recorded, never refused.

**SPIFFE is in the model (#1579)**, and the first whose wire is not JSON. A protobuf message is a model of fields, held by the build to the vendored `.proto` it stands beside: the protos stay verbatim and stay what grpc-js decodes with, because a local edit would give up interoperating with a real client, so the build's comparison is what keeps the two writings one — the alternative, the service loading its definitions from the model, is argued in `spiffe/CLAUDE.md` and is rcbj's to decide. What the protos cannot say is the model's alone: which fields are refused and in which words, the statuses each method answers, the SPIFFE ID grammar, an X509-SVID leaf's rules and the bundle's members. Answers are held before protobufjs serialises them, which is the one place a member that is no field is visible at all.

**SAML is the first XML protocol in the model (#1579).** Nothing about it is rendered: an XML parser, canonicaliser and signer stay in code (`common/xml_parser.js`, `common/crypto.js`), and what the model owns is what a hand-written builder used to decide — which value a URI is, which attributes are read and how, and the order of every attribute and child a builder writes. A builder that names a part the model does not, or one the signer inserts, throws, so the order cannot drift from the model in either direction. `tests/saml_model_wire.js` holds the switch byte for byte against a record of both identity providers made before it; `saml/CLAUDE.md`, *THE MESSAGES ARE THE MODEL'S*, says what stays in code.

**WS-Trust and WS-Federation are in the model (#1579), and with them every protocol family.** They are XML as SAML is, so they use SAML's decorators and reader rather than a lib of their own: `saml_lib.mjs` partitions the program by id prefix into `saml.json` and `ws.json`, `common/xml_model.ts` is the one reader (SAML's and the WS families' readers are its instances), and `ws.json` is read merged with `saml.json`, so an RSTR's SAML assertion is held to SAML's own message and a SAML term the WS families need (an assertion namespace, an authentication method `wauth` names) is that term, written as a TypeSpec property reference. What the model cannot own is the same as SAML's — parsing, canonicalisation, signing, encryption and every stateful check — and what `/sts` does not publish (WSDL, WS-MetadataExchange, WS-Policy) is stated in `ws/wstrust.tsp`. `tests/ws_model_wire.js` holds the switch byte for byte; `ws-trust/CLAUDE.md` and `ws-federation/CLAUDE.md`, *THE MESSAGES ARE THE MODEL'S*, say what stays in code.

**What #1390 listed is all in**, the real OID root included (#1573, under IANA's number 67607): domain concepts covering every directory attribute, generated classes and API types, generated validators, generated column upgrades, and Spectral and oasdiff gates. **`SCHEMA_UPGRADES` stays hand-written on purpose**: a key or routine change is a step between two versions, which one model of the end state cannot derive. **An entry's attribute is read through the concept that declares it** (#1579): `DomainMap.fromEntry()` or a generated class for a concept, `DomainMap.fieldOf()` for one field where a walk would otherwise make a whole concept per entry. Naming a field to `fieldOf()` is asking for it, so a secret field is answered there. `DirectoryEntry` carries what any entry has (`entryUuid`, the timestamps, `memberOf`). `tests/model_entry_reads.js` walks the service and fails on a modelled attribute read by its LDAP name outside the store, unless its `EXCEPTIONS` name the file and say why; each is argued again at the read. What stays by name, and why:

* **The store**: `ldap/ldap_server.js`, `ldap/directory_*.ts`, `persistence/`.
* **The browser bundles** (`web_*.ts`), including the console's by-name grids (`ldap/web_ldap.ts`, `spiffe/web_spiffe.ts`, `admin-ui/web_groups.ts`): they read an API answer, never an entry, and draw every attribute it holds.
* **A register's own codec**: `common/applications.js` and `federation/federation.js` turn an entry into the record their generated `SCHEMA` describes and back. The record round-trips to the directory, and a concept is one-way. A record's members are read by stored name in its consumers (`record.fedId`, an application's `fields.samlX` in `admin-core/`) for the same reason; a by-name HELPER over `fields` in a consumer is not, and was moved (GNAP, Kerberos delegation, delegation policy, AuthZEN, launch links, the SCIM client).
* **A table whose answer names the attribute**: the certificate pin audit (`<application> <attribute>`), the key pair and certificate subject tables in `admin-core/admin_views.ts`, the observed lists keyed by attribute, `DelegationPolicy.ATTRIBUTES` in the delegation pairs. Configured names are tables too: the claim catalogue and claim sets (`ssf/caep.ts`, `gnap/gnap_subject.ts`, `oid4vc/vc_claims.ts`), federation's attribute maps, a policy's `FIELDS` rows, `report/sources.ts`'s mechanism table.
* **A write, not a read**: a SCIM request converted to attributes, an entry moved between cells (`common/cell_rehome.ts`), a projection's `memberOf`, the SPIFFE registry's entries, `attribute_policy.ts`'s derived `cn` (read by first NON-EMPTY value, which no field states).
* **What no field can say**: `objectClass` (the model states an object's classes by `@entry`, not as an attribute), `userCertificate;binary` (a concept reads no LDAP option), every `mail` of an entry (the User has the first), `stsAttributeSingleValued`'s unreadable value (it must read as multi-valued; the concept leaves it out).
* **`stsAuthzenApplication` and `stsAuthzenCallbackUri` are declared on the person** (rcbj's decision on #1579, 2026-11-11; OIDs 746 and 747). Until then both were written and read but declared on no directory object, so the directory answered them in its folded spelling; it now answers the declared one.

`tests/tools/regenerate-model-docs.sh` rewrites the TypeSpec and the reading
pages, and a change to the model owes it. `tests/model_directory.js` and
`tests/model_postgres.js` fail when they differ. `node common/model_emit.js
--write` also writes `model.json` and `gaps.json`, which are not kept in the
tree.

The directory and table class text `model_emit` writes is not committed, because a
`.ts` file in this tree is compiled into the image and those classes serve nothing.
The concept classes and API types (`common/domain_classes.ts`,
`types/api.generated.d.ts`) are a different output, and are committed.
