Working inventory for phase 2 of the #94 database-layer decision
(issue #326, filed 2026-09-28). Delete this file when the move lands;
the lasting fact belongs in `persistence/CLAUDE.md`, not here.

The ticket's done condition is unchanged: the suite passes in every
mode, nothing imports `pg` outside the Knex layer, and `/admin/database`,

Knex 3 is already a dependency (`package.json`, used by attribute

## What "updated" means

Send each statement below through Knex. Keep the SQL text.

The ticket says the move is still PostgreSQL-only, with no change in
behaviour, and that LISTEN/NOTIFY, `pg_advisory_xact_lock`,
`ON CONFLICT` / `RETURNING` / `FOR UPDATE`, JSONB, the `pg_stat` probes
and `postgres/schema.sql` stay raw SQL. In this tree that is almost
every statement, not a short exception list. The rest are plain enough
that a query builder could express them, and still should not be
rewritten: `tests/directory_parent_statistics.js` and
`tests/directory_resident_walk.js` pin plans with `EXPLAIN`,
`tests/postgres_schema.js` pins the DDL text against `postgres/schema.sql`,
and `tests/cell_convert.js` pins one generated statement
(`DELETE FROM sts_realms WHERE id = $1`). A builder that emits different
SQL is a behaviour change.

Two mechanics have to be decided once, in the Knex layer, and then used
everywhere:

* **Bindings.** Every statement uses node-postgres `$1`…`$n` (and
  `$n::type`, `ANY($n::text[])`, `unnest($n::jsonb[])`). Knex's own
  bindings are `?`, which the PostgreSQL dialect renumbers. Keep `$n`
  and hand the text and the values to the connection Knex holds.
  Rewriting placeholders to `?` damages the statements that already
  contain `?` as PostgreSQL syntax, which Knex then reads as a
  binding (and `??` as an identifier). Those statements are listed
  under *The `?` operator* below. A literal `?` that must go through
  `knex.raw` has to be escaped Knex's way (`\?`), including the `?`
  inside `?|` and inside a jsonpath filter.
* **The clients Knex has to replace.** There is not one pool. The
  driver holds a write pool, a read pool, a dedicated liveness client
  (`liveQuery`), and a dedicated LISTEN client (`watchChanges` —
  a pooled client cannot LISTEN). `metrics` sets `statement_timeout`
  on the client it borrows and resets it. `queryWithoutJit` runs
  `BEGIN READ ONLY` / `SET LOCAL jit = off`. `guardClient()` exists
  because a pool that emits `error` kills the process. Bulk import
  and cell convert open pools of their own. The directory bridge's
  thread opens a client of its own from posted options (a function
  cannot be posted).

`DB_NOW` (`persistence_postgres.js` line 261,
`(extract(epoch from clock_timestamp()) * 1000)::bigint`) is spliced
into the cluster, claim and risk statements. It is not a query. Any
edit that turns those statements into builder calls has to keep
`clock_timestamp()` rather than `now()` or a JavaScript clock.

## The `?` operator

PostgreSQL's jsonb existence operators are `?` (one key), `?|` (any
key) and `?&` (every key). A jsonpath filter is also spelled `?`.
node-postgres binds `$n` and sends `?` through untouched, which is
why these statements work today. Nothing on this branch changed them.

`?&` is not used. The statements that contain `?` or `?|`:

| Where | What the `?` is |
|---|---|
| `directory_queries.js` `askedNamesExpression()` (608) | The jsonpath filter `$[*] ? (@ == "<name>" \|\| …)`. `ASKED_NAMES` (620) is that expression. The asked-names GIN index is built on it (`persistence_postgres.js` 557, `postgres/schema.sql` 268). |
| `directory_queries.js` `ASKED_NAMES_HELD` (631) | `attr_names ?\| ARRAY[…]`, the partial index's predicate. The same text is the index `WHERE` and the predicate a holder query repeats. |
| `directory_queries.js` `holdsClause()` (657, 668) | `ASKED_NAMES ? $n` for an asked name, or `attr_names ? $n` when the name has no index. |
| `directory_queries.js` `countHolding()` (725) | `attr_names ? $4` for an attribute the counters do not keep. |
| `directory_queries.js` `classesUnder()` (860) | `class_keys ?\| $3::text[]`. The index is GIN on `class_keys` with the default operator class, which is the class that implements `?` and `?\|`. |
| `persistence_postgres.js` `COUNT_NOTE_FUNCTION` (1641–1652) | `attr_names ? 'userpassword'` in the count trigger. `postgres/schema.sql` has the same function. |
| `persistence_postgres.js` `COUNTS_BACKFILL` (1889) | `attr_names ? 'userpassword'`. |
| `persistence_postgres.js` `resealSealed()` (8318) | `dek_keys ?\| $1::text[]`. The index is `USING gin (dek_keys)` with the default operator class (582), not `jsonb_path_ops`. |

The name, mail, uuid and value indexes are `jsonb_path_ops`, which
implements `@>` and does not implement `?`. Those lookups use `@>`
(`byName`, `byUuid`, `byMail`, `byAttribute`, `withNames`,
`HELD_NAME_KEYS`). That split is intact.

Attribute sources already pass `?` to Knex as a binding, in
`SELECT … WHERE <key> = ?`. Those statements contain no jsonb
operator. They are a different database and a different `?`.

`SELECT <columns> FROM <table> WHERE <key> = ?` with Knex, per dialect,
against an operator's database. That is phase 1. It is not this
service's store. Do not fold it into the driver's Knex instance.

by the database container as the owner. The driver's `SCHEMA_*` arrays

missing, because `sts_app` has no `CREATE`. `tests/postgres_schema.js`
fails when the two copies disagree. Move the execution onto `knex.raw`.
